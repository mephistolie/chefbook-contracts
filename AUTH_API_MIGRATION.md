# План реализации auth с начальной схемой БД

## Контракт шагов — локально реализован 2026-09-19

OpenAPI 0.5.0-draft, auth/gRPC, gateway, initial DDL и mobile адаптированы совместно.
Consumer snapshots совпадают с контрактом. Dev пока остаётся на 0.4.0-draft.
Проверки и платформенные ограничения: [AUTH_IMPLEMENTATION_STATUS.md](AUTH_IMPLEMENTATION_STATUS.md).

- Реализованы /steps/{stepId}/completion и плоские oneOf; start принимает только purpose.
- Регистрация: email без username → проверка email → пароль.
- Проверены предпосылки, flow binding, гонки, одноразовость, приватность до доказательства,
  stale alternatives, resend, запрет passkey/provider в signUp и секреты в ответах чтения.
- Новая начальная схема применяется только к отдельно выбранной пустой БД. Runtime
  отвергает прежнюю схему, не мигрирует и не удаляет её при старте.
- До выкладки нужны отдельное развёртывание backend/client и решение о dev-данных.
  Эта реализация не даёт разрешения очистить действующую БД.
- Passkey/VK native UI, автоматический reset deep link и реальные provider/device E2E
  остаются отдельными платформенными интеграциями. Лимиты расходов — отдельная задача.

## Предыдущая реализация

Зафиксировано 2026-09-17. Имя файла сохранено для существующих ссылок, но

## Этап 1. Материализовать контракт

- Перенести в source YAML все 38 операций из AUTH_API_DRAFT, убрать /auth prefix.
- Новые typed purpose, процессы, challenges и proofs; no top-level arrays;
  родители oneOf до вариантов, прямые ссылки на доменные схемы.
- signUp вместо POST /account; account после проверки, session отдельным POST;
  убрать регистрационную ветку email verification и emailVerificationRequired.
- sessions/{id}/tokens, общий DELETE sessions/{id}, password/reset, backup-codes.
- Grants вместо credentials в чувствительных операциях, исходная сессия и flow token;
  не включать client в login JSON. Conditional security документировать и проверять
  runtime-тестами; OpenAPI не выражает всю политику по purpose.
- GET состояния без выдачи plaintext secrets, attempt response без attemptId,
  200 вместо 201; /attempts остаётся ручкой, а не таблицей.
- Стандартные WebAuthn JSON DTO, типизированные provider/native варианты и nonce.
- Сохранить operationId существующих операций, где смысл сохраняется. Полностью
  заменённые операции не маскировать под прежнюю модель.
- Генерация bundle, validate и актуализация contract tests на новую таблицу маршрутов.
  Старый snapshot перевести в историческую справку; не тестировать новую модель как старую.
- Отдельно оценить поддержку выпущенных клиентов до выкладки несовместимых изменений.
  «Начальная БД» не означает автоматически безопасный deploy на работающий API.

## Этап 2. Начальный DDL и backend

- На пустой PostgreSQL создать согласованные таблицы сразу в итоговом виде.
  Проверить текущий runner миграций и выбрать его initial-schema entry point;
  не запускать всю прежнюю цепочку поверх нового init.
- Исключить roles/account_roles, abuse_counters, consumed_auth_proofs,
  firebase_accounts/imports, authentication_attempts и таблицы контекста цели.
- Не включать будущую sms-таблицу без реализации SMS. Нет universal JSONB для
  контекста auth: только JSONB outbox и явные типизированные расширения.
- Реализовать транзакции: финализация signUp, погашение grants, backup codes,
  TOTP replay, refresh rotation, регистрация passkey и удаление pending request.
- Реаутентификация через authentications; переиспользование реальных проверок
  только той же живой сессии, без продления времени выдачей новых grants.
- При изменениях credentials/факторов и восстановлении инвалидировать доверие и grants.
- Изменения таблиц в существующей runtime БД не выполнять автоматически. Подготовка
  initial DDL не требует переносить или удалять старые данные в этой задаче.
- Добавить разрешённый sessionId в JWT; ограничения и отзыв проверяются сервером.

## Этап 3. Gateway и клиент

- Gateway регистрирует новый API и auth policies; no-store/WWW-Authenticate/Retry-After
  действуют также на ошибках middleware. Проверить IDOR и все вложенные связи.
- Mobile обновляет snapshot/pin, генерирует DTO/API в impl соответствующих SDK.
  Локальные модели и офлайн-данные не переписывать под транспорт без необходимости.
- Общий UI прохождения следующего шага; факторы не ограничены first/second.
  Клиент не определяет, завершена ли проверка, и не выбирает обход требований.
- Регистрация без временной сессии; после завершения POST /sessions. Возможность
  работать локально сохраняется; нет обязательной регистрации при первом запуске.
- Нативные passkey/Google/VK SDK проверяются на реальных поддерживаемых сценариях.
  Android/iOS ассоциации домена и RP ID продумать до регистрации первых ключей.
- Существующую ConsumeReauthentication не удалять до полной замены provider binding.

## Проверки перед включением

- Повтор/конкурентное использование challenge, grant, refresh, backup code и TOTP.
- Два signUp с одним email/identity; сохранение владельца, отсутствие перезаписи пароля.
- Код другого процесса и письмо с другого устройства; потеря последнего ответа;
  неверный nonce, proof другого аккаунта/сессии, неподдержанный provider flow.
- Нельзя связать identity только совпадением email или только reauthentication grant.
- Отзыв сессии/фактора между challenge и конечным действием; окно доверия не продлевается.
- Последний способ входа нельзя удалить. Reset не отключает TOTP. Passkey UV обязателен.
- Account enumeration: одинаковое публичное поведение до доказательства владения.
- Все лимиты/очереди/расходы из отдельной задачи защиты проверены перед публичной регистрацией.
- Начальную схему и конкурентные операции проверить на настоящем PostgreSQL,
  consumer compilation — отдельно, затем end-to-end. YAML validation не заменяет этого.

## Детали, которые не следует выдавать за уже решённые

- Конкретные TTL и количественные лимиты; storage/алгоритмы защиты микросервисов.
- Provider SDK nonce/PKCE/auth_time, место typed nonce данных нативного флоу без state.
- Точная форма новых WebAuthn/provider DTO и недостающие коды ошибок.
- Состав RP/origin allowlist и dev/prod границы passkey.
- Очистка истории процессов после окна доверия, operational audit и реакция на сбои.
- Межсервисный исполнитель Firebase-импорта и уникальность исходного Firebase UID.

Таблицы и основной API согласованы; эти пункты — явные детали следующей реализации,
а не основание возвращать исключённые сущности без новой необходимости.
