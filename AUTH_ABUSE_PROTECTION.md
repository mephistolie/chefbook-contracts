# Защита микросервисов и расходов — отложенная задача

Решение 2026-09-17: таблицу abuse_counters сейчас НЕ включаем в начальную схему.
Выбор алгоритмов, общего хранилища и численных лимитов выносим в отдельное
проектирование защиты микросервисов. Ранее обсуждённые числа — идеи, не включённые
квоты и не обещание верхней границы облачного счёта.

## Что сохраняется в текущем дизайне

- TTL процессов, challenges, OAuth и заявок на изменение аккаунта.
- Одноразовость кодов и разрешений, атомарное погашение и проверка сессии/владельца.
- failed_attempts в authentications и authentication_steps, без журнала attempts.
- last_used_step в totp. Новая проверка не разрешает повтор уже принятого TOTP.
- Регистрация: временный процесс, собственный email-код, никакого аккаунта/сессии
  до финализации. Код привязан к исходному процессу. Нет старых restricted sessions.
- Ограничения аккаунта и проверки владения объектами остаются; отсутствие ролей не
  означает отсутствие авторизации. Ответы с секретами не кэшируются/не логируются.

## Что спроектировать отдельно

| Уровень | Механизмы |
|---|---|
| До приложения | Rate/concurrency limits на прокси, таймауты, размер тела, защита сети |
| Приложение | Ограничения по IP, аккаунту, адресу и операции, контролируемый расход CPU |
| Между экземплярами | Выбор PostgreSQL/Redis/другого storage общих счётчиков |
| Расходные операции | Общие дневные/месячные квоты писем/SMS и внешних вызовов |
| Исполнители | Скорость, предел очереди, TTL, bounded retries и повторная доставка |
| Эксплуатация | Метрики, уведомления, аварийное отключение платных операций |

Не считать IP единственной защитой: NAT объединяет людей, распределённая атака меняет
IP. При использовании прокси доверять forwarded IP только от известных прокси.
Не создавать безлимитное число ключей лимитера по пользовательским значениям.
Не блокировать навсегда чужой аккаунт по неаутентифицированным запросам.

Квота на постановку письма в outbox не ограничивает расходы на повторные отправки:
ограничения нужны и у отправителя. При невозможности проверить бюджет платную
операцию не запускать. Согласовать поведение при недоступности хранилища лимитов.

На старте допустим быстрый фильтр в прокси и устойчивые квоты редких операций в
PostgreSQL без Redis, но это ещё не утверждённая реализация. Не делать запись в
основную БД на каждый входящий пакет/HTTP-запрос под атакой.

## Перед публичным запуском

Минимальные ограничения регистрации, email/SMS, проверки паролей/кодов и ресурсов
обязательны. В частности, totp_activation_requests больше не содержит своего
failed_attempts: защитить активацию по аккаунту/временному окну вне этой записи,
не разрешая сбросить лимит пересозданием заявки. HTTP 429 в контракте не означает
работающий limiter. JWT и клиентские ограничения не заменяют серверную защиту.

Бюджет инфраструктуры — грант 18 тыс. рублей/месяц. Бизнес-квоты приложения не
ограничивают полностью оплачиваемый входящий/исходящий трафик, storage и логи.
Изменения Yandex Cloud/SWS/CDN/VM — отдельная инфраструктурная задача; Helluva не трогать.

Источники для отдельного этапа:
[OWASP DoS](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html),
[OWASP reset](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html),
[Nginx rate limits](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html),
[Redis rate limiter](https://redis.io/docs/latest/develop/use-cases/rate-limiter/).

В целевом API 0.5.0-draft пароль принимается только после emailVerification. Это уменьшает
неподтверждённые операции хеширования, но не заменяет лимиты отправки писем и нагрузки.
Ограничения/ответы до доказательства email не должны раскрывать существование аккаунта.
