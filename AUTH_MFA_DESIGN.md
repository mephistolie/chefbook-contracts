# Факторы и повторное подтверждение личности

Обновлено 2026-09-19 для API 0.5.0-draft; backend перенесён локально, без деплоя. Дополняет [API](AUTH_API_DRAFT.md) и
[начальную схему БД](AUTH_DATABASE_PLAN.md). Проверки и ограничения реализации —
в [AUTH_IMPLEMENTATION_STATUS.md](AUTH_IMPLEMENTATION_STATUS.md).
Прежние отдельные reauthentications, /sessions/confirmation и /account/reauthentication
заменены общими authentications/steps. В JWT добавляется только разрешённый пользователем sessionId для привязки к сессии.

## Вход

| Факторы | Последовательность |
|---|---|
| Пароль, TOTP выключен | Пароль → разрешение → POST /sessions |
| Google/VK, TOTP выключен | Проверенный provider proof → разрешение → POST /sessions |
| Пароль + TOTP | Пароль → TOTP или backupCode → разрешение → POST /sessions |
| Google/VK + TOTP | Provider proof → TOTP или backupCode → разрешение → POST /sessions |
| Passkey с серверно проверенным UV | WebAuthn proof → разрешение → POST /sessions; дополнительный TOTP не нужен |

Одного UP без UV для последнего варианта недостаточно. TOTP/backupCode не являются
самостоятельным первым фактором. Пароль не исключает остальные допустимые способы.
Без полного прохождения политик не выдаём access/refresh. Новый аккаунт дополнительно
проходит собственный email-код ChefBook, включая Google/VK; до завершения нет аккаунта
или регистрационной сессии. После emailVerification новый аккаунт завершает passwordSetup. Passkey и Google/VK можно подключить только после создания аккаунта. Сбор регистрационных данных и настройка credentials не считаются фактором реаутентификации.

## Свежая реаутентификация в той же сессии

1. Для sensitive purpose создаём authentications с account_id/session_id из bearer.
2. Ищем завершённый неинвалидированный процесс этой же живой сессии, содержащий
   реальные успешные проверки достаточного качества и свежести для нового действия.
3. Если найден, новый процесс сразу completed и выдаёт новое одноразовое разрешение.
4. Иначе предлагаем допустимые проверки; после них выдаём разрешение.

Разрешения остаются одноразовыми и имеют конкретный purpose. Реальные проверки
можно переиспользовать в пределах окна доверия. Отдельная таблица или новые поля
sessions для «последней реаутентификации» не нужны: время/методы в проверочных steps.

- Пример окна — 5 минут, не зафиксированная неизменяемая константа. Определить в
  конфигурации; срок итогового grant отдельно. Не продлевать окно использованием grant.
- Не ограничиваться самой последней записью: раньше могла быть более сильная ещё
  свежая проверка. Не соединять частичные проверки произвольных процессов.
- Автоматически completed процесс не создаёт новых успешных проверочных steps; сам по себе
  он не становится источником свежего доверия. Оцениваем фактические completion timestamps
  факторов, не время нового процесса или выдачи токена.
- Другая сессия не наследует доверие. Изменение credentials/факторов, reset и события
  восстановления инвалидируют затронутые процессы и grants. Отзыв сессии запрещает
  их использование. Проверять состояние снова в транзакции конечного действия.
- Нет universal admin bypass. Проверки прав на объект остаются в доменном сервисе.
- Достаточность зависит от purpose и текущих факторов. Password-only до подключения
  TOTP не должен после подключения разрешать отключение нового фактора.
- Вход как событие не автоматически даёт окно реаутентификации: использовать только
  явно разрешённые политикой процессы, привязанные к исходной сессии.

Проверка доступных методов строится сервером; OR-альтернативы и последовательные
требования не заменяются плоским «любой из всех методов». Новые виды подтверждений
добавляются как типизированные проверочные steps. Не раскрывать методы аккаунта до первого
доказательства при публичном входе; реаутентификация уже знает аккаунт из bearer.

## TOTP

- Один активный секрет в totp. Pending секрет в totp_activation_requests.
- После fresh totpEnrollment grant POST /account/totp выдаёт secret/otpauthUri и expiry.
  Клиент строит QR. setupToken отсутствует, подтверждение по исходной живой сессии.
- POST /account/totp/confirmation принимает первый код. Проверка, установка секрета,
  last_used_step, activation_timestamp и начальный набор backupCodes атомарны.
- Сразу учитываем первый код как использованный. Последующие принимаем только в
  допустимом временном окне и со step больше last_used_step; конкурентные проверки
  одного кода не могут обе завершиться успешно.
- Ключ шифрования вне БД. GET состояния никогда не возвращает секрет.
- При включении TOTP отзываем другие уже выданные сессии, чтобы refresh старых сессий
  не обходил новый фактор. Исходная сессия прошла повторную проверку и новый TOTP.
- Отключение требует достаточного proof, инвалидирует связанные процессы и текущий
  набор резервных вторых факторов. Это политика нынешней модели, коды не FK на totp.
- Pending setup истекает; отдельного cancel endpoint нет. Новая заявка заменяет secret.
  Общий лимит активационных попыток нельзя обнулить пересозданием заявки; механизм
  лимитирования отложен в задачу защиты, но обязателен перед публичным запуском.

## Passkey

- Несколько ключей на аккаунт, ключ может синхронизироваться между устройствами.
- Регистрация: fresh passkeyEnrollment grant → POST /account/passkeys/requests →
  requestId + стандартные WebAuthn options → системный диалог → POST /account/passkeys
  с requestId и attestation-ответом. Проверяем исходную сессию; сохраняем ключ и
  удаляем заявку атомарно. Никакого отдельного requestToken.
- Вход/реаутентификация: новые одноразовые assertions в общих challenges. Закрытый
  ключ и биометрия никогда не передаются серверу. Проверку выполнять библиотекой.
- Требуем проверку challenge, ceremony type, origin, RP ID hash, подписи, владельца,
  алгоритма, UP и UV. Discoverable credentials и userVerification=required;
  attestation=none для обычного потребительского приложения.
- user_handle — бинарный стабильный случайный UUID аккаунта; не email/username.
  Если позже добавляем колонку, существующие значения сохраняем. RP ID и допустимые
  origins задаёт сервер; dev/prod не смешивать без явного решения до регистрации ключей.
- Для mobile настроить Android asset links / iOS associated domains под выбранную
  интеграцию; наличие веб-проверки не означает работающую мобильную интеграцию.
- public_key хранится как COSE; sign_count/backup flags обрабатываются по WebAuthn,
  нулевой/немонотонный счётчик нельзя интерпретировать одинаково для всех credentials.
- transports — отдельная passkey_transports, не JSONB/массив в passkeys.
- PATCH имени не требует fresh proof, удаление — passkeyRemoval grant. Проверяем
  владельца и запрет удаления последнего способа входа. Сам grant не привязан к ID ключа.

## Резервные коды

- Имя backup-codes, method backupCode, поле backupCodes, таблица backup_codes.
- Начальный набор автоматически при успешной активации TOTP; повторный POST
  /account/backup-codes требует backupCodesRotation и заменяет набор атомарно.
- Plaintext показываем только при выпуске; храним HMAC высокоэнтропийных случайных
  кодов, ключ вне БД. DELETE RETURNING и завершение проверки в одной транзакции.
- GET отдаёт remainingCount и generationTimestamp. После использования всех кодов
  дата null: отдельную историю наборов не заводим.
- Потеря ответа выдачи кодов не даёт GET plaintext: после подтверждения можно
  перевыпустить. Код заменяет дополнительный фактор, а не пароль/провайдера сам по себе.
- Reset пароля не отключает MFA. Потеря всех факторов требует отдельной политики
  восстановления/поддержки, а не автоматического обхода через email.

## Провайдеры

consumed_auth_proofs не создаём. Серверный nonce связывает ID token с одноразовым
challenge; code/state/PKCE флоу проверяются адаптером. Подробнее в OAuth-разделе
AUTH_DATABASE_PLAN.md. Перед включением подтвердить поддержку конкретными SDK,
проверку nonce в подписанном токене и невозможность использования proof в другом
процессе/сессии/назначении. Нативный флоу без state требует typed nonce context.

Свежий токен не равен свежей авторизации: auth_time/требование повторной проверки
провайдера обосновываются отдельно. Не рекламировать способ реаутентификации, пока
такие гарантии не реализованы. Identity linking требует отдельного proof новой
identity даже при недавней реаутентификации ChefBook.
