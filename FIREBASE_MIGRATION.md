# Однократный импорт пользователя из Firebase

Согласовано 2026-09-17. Реализация отдельно от начальной SQL-схемы auth.
Firebase после переноса пользователя не нужен для его обычной работы.

## Граница ответственности

В auth НЕ создаём firebase_accounts или firebase_imports. После доказательства
права на legacy-аккаунт и определения Firebase UID создаём аккаунт/связанные данные
и записываем событие с accountId/firebaseId в outbox одной транзакцией.
Outbox обеспечивает возможность повторной публикации; очередь допускает повторную
доставку. Auth не ждёт переноса рецептов и не хранит его прогресс.

Исполнитель миграции отвечает за:

- уникальное соответствие Firebase UID целевому аккаунту вне БД auth;
- перенос рецептов, коллекций и связей;
- отсутствие дубликатов при повторной команде;
- успешное завершение и возможность продолжить после частичной ошибки;
- сопоставление исходных ID целевым или детерминированные ID;
- временный учёт прогресса/контрольных точек, если перенос выполняется порциями.

Наличие события в outbox НЕ доказывает завершение импорта. Нельзя отмечать импорт
выполненным перед сохранением данных. Конкретную схему исполнителя не включаем
в согласованные таблицы auth. Отдельный микросервис ради этого не обязателен.

## Подтверждение владельца

Старый Firebase-пароль не делаем обязательным. Пользователь доказывает доступ к
прежнему email кодом ChefBook в исходном процессе регистрации/восстановления.
Совпадения строки email без доказательства недостаточно. Новый signUp не может
перезаписать credentials уже перенесённого аккаунта: нужен обычный вход/password reset,
с сохранением MFA. Ошибка Firebase не означает, что legacy-аккаунта нет.

До включения нужно определить источник/процедуру разрешения Firebase UID (например,
проверенный экспорт и mapping у мигратора). Удаление mapping из auth не снимает
требование уникальности: нельзя перенести один UID разным аккаунтам. Это отдельная
деталь реализации, не повод тихо восстанавливать firebase_accounts в auth.

## Что обнаружено в текущем коде

Это наблюдения по репозиторию, не проверка развёрнутого окружения:

- Обычный SignUp по email импорт не запускает.
- SignIn при отсутствии пользователя в локальной БД пробует Firebase credentials.
- Создание пользователя через Google/VK запускает фоновый поиск по email.
- Связь firebase и событие пишутся атомарно, но создание самого пользователя и
  фоновая привязка разделены; при ошибке привязки нет надёжного задания на повтор.
- Recipe importer отмечает inbox до сохранения рецептов; повторная отметка возвращает
  nil, и вызывающий код продолжает импорт. Новые UUID могут приводить к дублям.
- Ошибки отдельных рецептов/коллекций/избранного не всегда поднимаются наверх;
  завершение обработки сообщения не гарантирует полный перенос.

При будущей реализации исправить эти свойства, а не копировать текущий importer.
Повторная доставка события, падение после сохранения порции и гонка двух исполнителей
должны быть проверены. Сейчас код, credentials и реальные пользовательские данные
не менялись.
