# Состояние реализации auth

## Типизированные шаги — реализовано локально 2026-09-19

Auth, gateway и mobile перенесены на OpenAPI 0.5.0-draft. Контракт и оба consumer
snapshot совпадают: SHA-256 `ceca254a292784d193819f8a8e843b51c62809ea9ddec4dfff4be8ef6b2b5d2b`.
Dev остаётся на 0.4.0-draft: новые бинарники/клиент не опубликованы и не развёрнуты.
Реальные базы и облачные ресурсы не изменялись. Ниже сохранена история предыдущей версии.

- Вместо challenge endpoints — /steps и /steps/{stepId}/completion; purpose-only start.
  Все 9 вариантов шага имеют плоские типизированные тела с type; старые тела отвергаются.
- Регистрация: только email → код в исходном flow → установка пароля.
  Username выбирается позже; наличие аккаунта раскрывается лишь после правильного кода.
- Сервер проверяет предпосылки при старте и завершении; stale alternatives отменяются,
  повторы не создают второй credential/grant. Проигравшая гонка email завершает процесс
  failed с account_exists, сохраняя существующий аккаунт и его способы входа.
- Initial DDL: 20 таблиц, authentication_steps и типизированные расширения.
  Регистрация — только email и пароль; ID аккаунта создаётся при финализации. Аккаунт/credential/outbox/grant создаются атомарно.
  Runtime требует новую схему и не преобразует старую автоматически.
- WebAuthn GET строит параметры из сохранённого challenge/UUID/expiry без нового ceremony.
  Настройка credentials не считается доказательством для повторной реаутентификации.
- Gateway сериализует options/steps как массивы, OAuth URL/nonce только при старте шага,
  flowToken только при создании процесса, grant только в завершающей мутации.
- Mobile: генератор поддерживает DTO сразу в двух oneOf; SDK и экраны используют новые
  шаги. Первый экран регистрации больше не собирает пароль. После кода показывается
  установка пароля. Google доступен при входе; Android передаёт серверный nonce в SDK.
- Восстановление пароля получило рабочие экраны запроса письма и ввода токена/ссылки
  с новым паролем вместо TODO. Автоматический deep-link переход из почтового клиента
  ещё не подключён. Секреты незавершённого процесса хранятся только в памяти.

Проверено:

- 40 контрактных тестов, внешний OpenAPI validator и 105 JSON-примеров.
- Полный gateway `go test ./...`, повторно с финальным auth protobuf; generated parity.
  HTTP-тесты покрывают все варианты completion, запрет старых/смешанных тел, binding,
  Location, 409 account_exists и отсутствие секретов в чтениях.
- Auth `go test -race ./...` на временной локальной PostgreSQL 17: 56 верхнеуровневых
  тестов / 104 с подслучаями, без пропущенных тестов. Проверены интеграционные,
  runtime и schema сценарии. Nested protobuf API module также собирается.
- Проверены гонка одного email, атомарность account/outbox/grant, реальные подписи
  WebAuthn, invalid origin, replay, предпосылки setup, flow isolation,
  resend/expiry и запрет переиспользования setup как реаутентификации.
- Mobile: 16 auth SDK + 9 auth core/UI-state тестов; 7 Python-тестов
  генератора, проверка generated parity и компиляция auth Compose для Android.
  Проверены плоский oneOf, два родительских интерфейса DTO, отсутствие раннего пароля,
  Google nonce/terminal cleanup, следующие варианты и восстановление пароля.

Ограничения перед выкладкой: системный passkey/VK UI клиента пока не подключён;
Android Google, SMTP и браузерные callback/deep links не проверялись на реальных
аккаунтах/устройствах. Passkey доступен на сервере и в сгенерированном SDK; неподдержанный
клиентский шаг не пропускается. Исходная PostgreSQL схема и несовместимый протокол
требуют отдельного согласованного развёртывания, не автоматического сброса dev.

## Предыдущая реализация

2026-09-17. Изменения локальные, без публикации контрактов и без деплоя.
Действующие базы данных и облачные ресурсы не изменялись.

## Реализовано

- OpenAPI `0.4.0-draft`: все 38 согласованных операций, типизированные purpose,
  challenges/proofs, flow token и отдельные одноразовые grants.
- Gateway: новые маршруты и DTO связаны с типизированным AuthenticationService gRPC;
  проверяются живые сессии и текущее состояние аккаунтов. Ответы auth не кешируются.
- Auth: регистрация до создания аккаунта, email-код в исходном процессе, вход,
  refresh rotation, отзыв сессий, реаутентификация и повторное использование свежих
  проверок без продления доверия, пароль/reset, username, email change, удаление,
  identities, TOTP/backup codes и WebAuthn passkeys.
- JWT: разрешённый пользователем ID сессии передаётся в claim `sid` строкой,
  чтобы сохранять точность BIGINT. Новых claims разрешений/capabilities нет.
  JWT без sid не даёт доступ к новым защищённым операциям: нужен повторный вход.
- Начальная схема: 20 таблиц, включая отдельный Google nonce challenge.
  `schema.Initialize` создаёт их транзакционно только в пустой схеме.
  `cmd/migrations` теперь требует явный `--initialize`, старую цепочку не запускает.
  Runtime проверяет схему, но не создаёт и не изменяет её автоматически.
- Mail: отдельный сервис с versioned MQ сообщениями и SMTP/Postbox. Auth пишет
  письмо в одной транзакции с изменением состояния; publisher использует persistent
  mandatory delivery и broker confirms. Отправитель noreply, Reply-To не добавлен,
  dev-префикс сохранён. Старый SMTP-воркер auth не запускается.
- Клиент: обновлены контракт и генерация, существующие экраны входа/регистрации/
  удаления поддерживают многошаговый процесс. Refresh/logout используют sessionId;
  debug-логи не содержат auth body и секретных заголовков.
- Старый внутренний AuthService сохраняет read-only RPC для других микросервисов.
  Старые mutation RPC не регистрируются как обход нового процесса.

## Проверки

- OpenAPI bundle, внешний validator, 24 теста контракта.
- Побайтовое совпадение контрактов gateway/mobile с source и SHA-256 lock.
- Полный `go test ./...` gateway; `go test -race ./...` auth с реальной
  PostgreSQL, mail с mock SMTP, тесты общего tokens-модуля.
- Мобильные тесты: 27 auth/profile/UI плюс 2 network, 6 Python generator tests;
  компиляция затронутых Android SDK/Compose/root navigation модулей.
- Реальные WebAuthn подписи P-256 и attestation, положительные/отрицательные
  проверки challenge/origin/RP/signature/UV/counters; race tests.
- Временная локальная PostgreSQL: DDL/constraints, одноразовость grant/refresh/
  backup code при конкуренции, original-flow email proof, TOTP replay, отсутствие
  продления доверия, отзыв сессии и атомарность outbox/challenge rollback.
- OAuth с тестовым провайдером: чужой flow не расходует state, state одноразовый,
  nonce и auth_time проверяются; provider-регистрация также требует email-кода.
- Реальный gRPC через bufconn: полный signup → code → grant → session → refresh →
  revoke, проверка RSA/JWT/sid и машинных кодов ошибок. Неудачный initial DDL
  откатывается целиком; повторный init заполненной схемы безопасно отклоняется.
- Повторная регистрация: account_exists выдаётся только после правильного email-кода;
  прежний пароль не изменяется, клиент показывает локализованное предложение войти.
- Двухэтапная смена email, сброс пароля с отзывом сессий и дедлайн удаления
  дополнительно проверены на PostgreSQL; SQL-ошибка приведения timestamp исправлена.

## Что ещё требуется перед включением

- Новые native Google/passkey ceremonies и экраны управления MFA/ключами на клиенте
  остаются отдельной интеграцией. Наличие сгенерированных методов не означает готовый
  интерфейс. Старые TODO навигации password reset также отдельно.
- Настроить стабильные HMAC/AES/signing keys, Postbox/очереди, реальные callback URLs,
  RP ID/origins и Android/iOS domain associations. Новые ключи не генерируются молча
  при рестарте; их значения должны храниться вне репозитория.
- Google реаутентификация требует проверенного nonce и свежего `auth_time`.
  Legacy VK не даёт `auth_time` и PKCE: только HTTPS callback для его code flow;
  свежая реаутентификация таким ответом запрещена. Для расширения нужен modern VK ID.
- Абьюз-защита и глобальные ограничения расходов всё ещё отдельная задача.
  Лимиты попыток процессов сохраняются в PostgreSQL; временный лимитер активации TOTP
  локален инстансу. Он не заменяет общие ограничения нескольких реплик.
- SQL-переходы первоначально сериализованы advisory lock PostgreSQL. Это обеспечивает
  согласованность отзыва/одноразовых доказательств между инстансами, но ограничивает
  пропускную способность, в том числе при bcrypt-проверках. Провайдерская сеть вне lock.
- Firebase runtime fallback выключен: согласованный одноразовый импорт требует
  отдельного исполнителя и проверенного сопоставления старых UID, он не завершён здесь.
- Mail имеет at-least-once доставку: возможны дубликаты при аварии между SMTP и ACK.
  Реальные SMTP/провайдеры, брокерная доставка и устройства не проходили live E2E.
- Полный production rollout, обратная совместимость выпущенных клиентов и сборка
  контейнеров в окружении публикации требуют отдельной проверки. Docker-контекст
  auth/gateway теперь корень backend workspace с локальными API/token модулями.
